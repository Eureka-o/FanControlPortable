# 黑鲨风神 PRO（BRB02）设备接入说明

日期：2026-10-24
固件基线：`3.0.3`（由 `0x01` 读取）

本文记录黑鲨风神 PRO 散热器的设备档案、功能范围、通信协议与出厂参数，供后续维护、协议比对与升级适配时查阅。

代码分层：协议事实（帧、命令表、标定表、出厂常量）在 `internal/deviceproto`，
设备读写与链路状态在 `internal/device`（BLE 侧经 `internal/deviceprofileexec`），
编排与策略在 `internal/coreapp`。本文按**符号名**检索，行号不作保证。

文中标"实测"的条目来自真机读取或字节级复现；标"（推断）"的条目尚未取得字段名级或行为级证据，
修改相关代码前应先补齐证据。

## 1 概述

### 1.1 设备档案

设备按传输拆成两个内置档案，二者共用同一套应用层帧，能力位也相同：

| 档案 ID | 传输 | 说明 |
|---|---|---|
| `builtin.blackshark.brb02.ble.rpm` | BLE | 默认档案；按设备名过滤 `BS BRB02 Cooler Pro` |
| `builtin.blackshark.brb02.usb.rpm` | USB（WinUSB） | VID `0xE2B7` / PID `0x7001`，经 libusb 访问批量端点 |

已退役的档案 ID `builtin.blackshark.brb02.hid.rpm` 在连接与设备扫描时被直接跳过
（`isLegacyBlackSharkHIDProfileID`），不再参与控制。

两个档案都声明 `SupportsScreenImageTransfer`：图传的两条通路都已实现，差别只在时间预算
（见 §4.3）。灯效、亮度、挡位灯与屏幕这几项能力位恒为 false —— 声明为真会点亮上游那套通用面板，
形成同一功能的第二份界面，并让"把主机侧灯带配置推给设备"的路径对黑鲨生效；
黑鲨的灯效由设备自己持有，由本项目的黑鲨面板负责。

### 1.2 覆盖情况

| 维度 | 官方（黑鲨装备箱） | 本项目 | 覆盖 |
|---|---|---|---|
| 功能页 | 6 页 + 首页仪表盘 + 设备展示 + 固件升级 | 主界面转速/曲线 + 黑鲨面板 + 屏幕区 | 见 §2.3 |
| 命令表 | 31 条（app 侧 mission 29 个，DLL 18 个） | 26 条端到端实现，2 条只登记，3 条黑名单 | 见 §2.5、§3.3 |
| 不可逆能力 | 完整（进 BOOT、刷固件、恢复出厂） | 不提供 | 见 §2.3 |

散热（固定转速、四档、散热模式、温控参照）、灯效（8 种模式及颜色/亮度/速度，含两个需要主机推送数据的模式）、
屏幕（预设图、本地上传与裁剪、显示参数、从设备读回）已与官方等价。情景改为主机侧规则引擎实现，
可观测行为等价。固件升级、进 BOOT、恢复出厂、产线命令不提供（不可逆操作）；
恢复出厂由可逆的「配置快照导出/还原」替代。

命令表里 2 条只登记不发送（`0x20`、`0x27`），3 条列入危险命令黑名单（`0x04`、`0x05`、`0xF0`），
其余 26 条都有明确的读写路径。

需要注意：当前验证基线是"已实现的部分与官方一致"，不是"官方能做的本项目都能做"。后者未经系统性核对，
因此不宜用单一百分比描述替代完成度。

### 1.3 速度单位

本项目统一使用转速 RPM。官方界面使用百分比滑块（10~100，不显示数值），
其与设备设定值的关系为 `sp = 1200 + (pct − 10) × 2800 / 90`（实测 5/5 吻合，取整方式为向上取整）。
官方没有 sp↔RPM 换算，本项目的 sp↔RPM 标定表为自行实测所得，见 §3.7。

## 2 与官方黑鲨装备箱的功能对照

### 2.1 官方功能结构

官方界面由 `formBRB02*` 系列页面装配函数构成：

│   └─ _Light_Config
├─ formBRB02Functions_Scene              情景：规则 + 进程项

| 实时转速显示 | `0x06` u16le，约 2 Hz | `BlackSharkStatusRPM` + 收帧状态机 | 对齐 | 第三字节是供电模式位，见 §3.5 |
| 固定转速 | `0x24` 固定形态（5 B） | `EncodeBlackSharkFixedSpeedPayload` | 对齐 | 首次写入走完整 apply 仪式，见 §6.2 |

### 2.4 实现方式上的差异

| 项 | 官方 | 本项目 | 说明 |
|---|---|---|---|
| 情景 | 设备侧 `0x08` + 4 槽位 | 主机侧规则引擎 | 官方勾选槽位不产生设备流量（实测） |
| 变频由谁算 | 设备侧跟随（曲线写进设备） | 两套可选，见 §6.2 | 主机侧调速是上游同款形态，作为可切换项保留 |
| 屏幕尺寸 | 要求尺寸大于屏幕 | 任意尺寸等比缩放 + 居中裁剪 | — |
| 写命令确认 | 消费每个写命令的 ACK | 写 ACK 与读回分别裁决 | 两者覆盖的问题不同，见 §5.3 |
| 颜色控件不可用时 | `setVisible(false)` 隐藏 | 置灰并附一行说明 | 置灰不会给出"可用"的暗示 |
| 图传编排 | 独占任务，期间暂停周期推送 | 独占任务 + 暂停 `0x07` 推送 + 按通路预算 | 见 §4.3 |
| 状态读取 | 每次进页面现读 | 本机落盘缓存 + 后台回读校验 | 见 §6.3 |

另有两点无法通过逐帧比对发现：

- **状态机与时序**：官方 DLL 是请求-应答状态机（内部排队、超时、回调续延）；本项目用"一个串行器 + 一次交换"
  达到同形语义（见 §3.6），但在并发、异常、设备无响应等场景下官方处理更完整。
- **通道冗余**：官方有 USB 与蓝牙两条通道，本项目两条都实现，能力位一致。

### 2.5 官方软件的三套实现与对接策略

| 实现 | 路径 | mission | 传输 |
|---|---|---|---|
| app | `BlackSharkEquipmentBox.exe` | 29 | 自带 libusb |
| 常驻服务 | `Brb02Service.exe` + `Brb02CoolerComm.dll` | 18 | DLL 自带 libusb / 蓝牙 / socket |
| 本项目 | `internal/deviceproto` 等 | 26 条命令端到端 | WinUSB（libusb）与 BLE 两条 |

对接策略：

- **真值来源取 app**。它是能力超集，且 UI 逻辑可反汇编，能取得 DLL 无法提供的"选项名与数值的对应关系"。
- **DLL 仅作开发期的帧级预言机**（32 位，`GOARCH=386`，一进程一调用，不进入产品）。已用其产出 34 条向量完成逐字节对齐。
- **产品实现为 64 位原生代码**，不依赖任何官方二进制。

不把 DLL 作为引擎的原因：app 并不导入 DLL（只有 `Brb02Service.exe` 导入），
且 DLL 对 BRB02 的能力是 app 的子集（18 对 29）。改接 DLL 会丢掉 14 项 app 独有能力，
并引入 32 位宿主进程、IPC、崩溃隔离、"用户必须安装官方软件"、DLL 版本漂移五类成本。

DLL 导出表中可直接产出帧的接口：

| 功能 | DLL 导出 |
|---|---|
| LCD 显示位置 `0xC2` | `coolerSetLcdShowPos` |
| 恢复出厂 `0xF0` | `coolerRestoreFactorySettings` |
| 设备总开关 `0x27` | `coolerSetDeviceSwitch` |

`coolerSendPacket`、`coolerGetDeviceInfo` 不是导出，它们是 DLL 内部的 mission 名。

## 3 通信协议

### 3.1 设备标识与传输

**USB（WinUSB / libusb）**

| 项 | 值 |
|---|---|
| VID / PID | `0xE2B7`（58039） / `0x7001`（28673） |
| 驱动 | WinUSB（厂商自定义 Usage Page `0xFFA0` / `0x0002`） |
| 端点 | OUT `0x01`，IN `0x81`（描述符为中断类型，经 libusb 的 bulk API 访问；Windows/WinUSB 对中断管道同样接受） |
| 接口 | 0，打开后先 `libusb_set_auto_detach_kernel_driver` 再 claim |
| 报文长度 | 65 字节 |
| 依赖 | 随包放在 exe 旁的 `libusb-1.0.dll`；必须用 `NewLazyDLL` 而不是 `NewLazySystemDLL`，否则只在系统目录搜索会找不到 |

**BLE**

| 项 | 值 |
|---|---|
| 名称过滤 | `BS BRB02 Cooler Pro` |
| 写特征 | `ae41`（所属服务 `AE40`） |
| 通知特征 | `ae04`（所属服务 `AE30`） |
| 写方式 | 无需响应（write without response） |
| 服务发现 | 留空，交给客户端自行发现两个服务 |
| 发送间隔门 | 档案里显式设为 `-1`（取消上游默认的 100 ms 门） |

**报文封套**

帧本体在报文里的位置随传输不同，两条通路长度一样、线上只差 1 字节：

| 传输 | 封装 | 设备实际收到 |
|---|---|---|
| libusb 直连端点 | 帧 `@0` + `0x00` 填充 = 65 字节 | 帧 `@0` |
| HIDAPI / HIDClass | `0x00`（ReportID 占位）+ 帧 + `0x00` 填充 = 65 字节 | 帧 `@0` —— ReportID 由 HID 协议栈吃掉，不到设备 |

封套由 `blackSharkBuildReportForHandle` 按句柄选（判据与 `WriteReport` 内部分支同一个：`usb != nil` 即 libusb），
保证"装的报文"与"句柄发的方式"不分叉。写错封套不会立刻被拒（设备不校验 CK），
只会在很后面以"设备不再回某条命令"的形式暴露。

**链路判据（四者刻意不合并）**

| 判据 | 回答的问题 |
|---|---|
| `blackSharkHandleLocked` | USB 句柄在不在手（已连接 + 黑鲨档案 + `m.flyDigiHID != nil`） |
| `blackSharkBLESenderLocked` | BLE 执行器已连且档案属于黑鲨族、传输是 BLE |
| `blackSharkLinkReadyLocked` | 现在能不能换帧（上面任一成立） |
| `blackSharkCanWriteLocked` | 非悬挂期 + 链路就绪（写权限） |

黑鲨与飞智共用同一个句柄字段（`m.flyDigiHID`），所以"这个句柄是不是黑鲨的"必须同时看
**已连接 + 句柄在手 + 当前档案属于黑鲨族**；只看句柄非空会把飞智设备当成黑鲨，
使黑鲨面板与读图路径在飞智设备上被激活。

**连接补充**

- BRB02 配对后空闲时不广播，名称扫描扫不到，只能按地址直连：`ConnectBlackSharkBLEDirect`
  从 Windows 配对表取地址，失败再回落候选表的名称扫描。
- 两条通路各有存在性探针：`BlackSharkBluetoothAvailable`（适配器可用性，不扫描不连接）、
  `BlackSharkUSBInterfacePresent`（枚举探针，打开即关；调用方不得持 `m.mutex`）。

### 3.2 帧格式与校验和

```
偏移 0     : 0xA5            魔数（控制族）
偏移 1     : LEN             整帧长度 = 4 + len(PAYLOAD)
偏移 2     : CMD             命令码
偏移 3..   : PAYLOAD
偏移 LEN-1 : CK              校验和
```

报文固定 65 字节，构造与读写见 §3.1。

| 方向 | CK 规则 | 实现 |
|---|---|---|
| 主机 → 设备 | 字节和取低 8 位（设备不校验） | `deviceproto.BlackSharkChecksum` |
| 设备 → 主机（对主机请求的应答） | CRC-16/XMODEM 低字节（poly `0x1021`、init `0`） | `deviceproto.BlackSharkRXChecksum` |
| `0xA4` 数据族 | 字节和取低 8 位 | — |
| 设备主动上报（`0x06`，约 2 Hz） | 字节和取低 8 位 | — |

回帧的规则按命令登记在 `BlackSharkChecksumRules`（唯一所有者）。解析时两条规则都会试，
但会把"登记哪条"与"实际命中哪条"一并带出 —— 两者不一致本身就是诊断信号：
**同一条 `0x07` 在 BLE 上走字节和，在 USB 上走 CRC16**。

CRC 这一支的参数是 init `0x0000`，标准名是 XMODEM；CCITT-FALSE 是 init `0xFFFF` 那一支，不要混用。

两条需要注意的性质：

1. CK 不是有效性机制，不能用 `ChecksumOK` 判断帧是否有效；
2. CK 不能用于反推帧方向 —— 设备主动上报走字节和，按 CK 规则判方向会得到错误结论。

设备使用两个 magic：控制族 `0xA5`，数据族 `0xA4`（屏保图像与预览动画）。

### 3.4 主机侧帧构造点

对官方 exe 中调用校验和追加函数（`call 0x544160`）的位置做机械枚举，

### 3.5 设备侧回帧

**回帧入口**为 `0x54616a`：`cmp al,0xA4` 转 `0x5458f0`，`cmp al,0xA5` 转 `0x544e20`，其余 magic 打印未知包头。
`0x544e20` 内为跳转表（索引表位于 `0x5457f8`，跳转表位于 `0x54579c`），
共 22 个命令有专门处理器，其余一律走 default（`0x545789`，收到即忽略）：

```
0x01 0x02 0x03 0x05 0x06 0x10 0x11 0x12 0x13 0x14 0x22
0x24 0x25 0x26 0xC0 0xC1 0xC4 0xC5 0xC6 0xC7 0xC8 0xF0
```

`0x04`、`0x08`、`0x07`、`0x23`、`0x20`、`0x27` 均落在 default 中，
即官方发送这些命令，但收到回帧后不做任何处理。

**真机回帧统计**（按抓包工具自带的 tx/rx 方向标签统计，不使用 CK 反推）：

| cmd | rx 帧数 | 结论 |
|---|---|---|
| `0x01` / `0x02` / `0x03` | 2 / 8 / 4 | 设备回帧 |
| `0x06` | 1396 | 即设备主动上报本身 |
| `0x07` | 993 | 设备回帧 |
| `0x08` | 8 | 设备回帧 |
| `0x10` / `0x11` / `0x13` | 2 / 2 / 2 | 设备回帧 |
| `0x14` | 18 | 设备回帧 |
| `0x24` / `0x25` / `0x26` | 9 / 7 / 28 | 设备回帧 |
| `0xC0` / `0xC1` | 2 / 6 | 设备回帧 |
| `0xC2` | 14 | 设备回 ACK，重复写入相同值也会回；ACK 不携带参数值，是 `0xC2` 唯一的确认手段 |
| `0xC4` / `0xC5` | 8 / 12 | 设备回帧 |
| `0xC6` | 16768 | 上传流控，由设备主动发起 |

**载荷布局**

`0x06` 状态上报，3 字节：

```
[rpm u16le][供电模式位]    0x00 = USB 供电，0x01 = 专用电源
```

该位只原样带出、不映射成挡位名；写控速不改变它。

`0x12` 灯效，8 字节：

```
[0]     低 4 位 = 模式槽位 (1..8)    高 4 位 = 颜色选项序号 (0..4)
[1..2]  u16le = 速度（直通，即界面滑块的当前值，无映射）
[3]     亮度 (0..100，默认 0x50 = 80)
[4]     0x0A 彩色 / 0x01 单色
[5..7]  大端 R,G,B
```

`0x24` 冷却，固定形态 5 字节 / 曲线形态 15 字节：

```
固定形态 (form = 0x00): [src][00][gear] + 转速 sp u16le                =  5 字节
曲线形态 (form = 0x01): [src][01][gear] + 4 × (温度 u8, 转速 u16le)    = 15 字节
  gear = 1..4，对应低噪 / 平衡 / 强效 / 超频；曲线固定为 4 点
  src  = 冷却参照源：0 = CPU(id0)，非 0 = GPU(id1)
```

设备按 `(gear, form, src)` 三键存配置：只写一个 `src` 会让另一个 `src` 缺这份配置，
下次用它当参照源时读不到。而 `byte[0]` 同时是"写哪一份"，写完设备就切过去了 ——
所以曲线形态按两个参照源各写一遍，次序由 `BlackSharkCoolingSourceWriteOrder` 定：
当前源放最后一次写，两个源都拿到新值，设备生效的参照源不变。
固定形态只写当前那一个源（抓包里固定形态的两次写用的是同一个 `src`）。

曲线里的温度字段设备不校验，取值为产品约定：
用户的 4 个点可在 `BlackSharkCurvePointMinTempC..MaxTempC`（10 ~ 100 ℃）内取任意整数温度；
下发前会按 `ClampBlackSharkCurveRPM` 把转速夹进可达区间并量化到 30 RPM。

`0x07` 系统信息（主机 → 设备），22 字节：

```
[条数] + N × (id u8, 值 u16le)      N = 7，故总长 22
id: 0 CPU温度  1 GPU温度  2 CPU负载  3 GPU负载（恒 0）  5 磁盘（恒 89）  6 运存  7 时间（时 × 60 + 分）
    推送集固定这 7 项，不含 id 4（风扇转速）；id 4 只出现在 LCD 可选显示项里
```

冷却参照源决定设备跟随 `0x07` 的哪一项温度：`src = 0` 跟 `id0`，非 `0` 跟 `id1`。
设备只回空载荷 ACK、不回显收到的值，因此只能确认"已发出且被 ACK"。

`0x15` 与 `0x16`：

```
0x15:  A5 05 15 <档位 0|1|2|3> CK   约 4.9 Hz，持续流
0x16:  A5 04 16 CK（空载荷）        事件驱动，每次按下
```

`0x15` 的帧载荷就是档位，是**持续流**而不是"设置一次的值"：静音时发 `0`。
按"静音就不发"实现会让设备停在最后一档，因为设备不会自己回落。

`0xC2` LCD 显示参数，长度 `3 + 4n`：

```
头 3 字节  = [pos][00][条数]        pos 只接受 0
每条 4 字节 = [id u8][x u16le][y u8]
    实测（pos = 0，三格）：x = 10 / 143 / 276，y = 0x64 = 100
    默认三项 id = 00 CPU温度 / 01 GPU温度 / 07 时间
实测整帧：a5 13 c2 00 00 03 | 00 0a 00 64 | 01 8f 00 64 | 07 14 01 64 | 5f
```

条目必须为 4 字节，按 3 字节发送会被设备整帧拒绝。该命令无值读回，ACK 是唯一确认手段。

`0xC4` 屏保图像信息帧，11 字节载荷：

```
[0..3]  u32 小端 = 写入时刻的 Unix 秒（官方取 QDateTime::toTime_t()，同值还用作屏保 .bin 的文件名）
[4..7]  u32 小端 = 画布字节数（428×142×2 = 121552）
[8..9]  u16 小端 = 画布的 CRC-16/XMODEM（poly 0x1021、init 0）
[10]    0x00
```

设备当前不校验时间戳。实现按当前时刻取值而不是写死常量：一旦固件开始校验，陈旧常量会让整轮上传被拒收。

`0xC6` 流控应答，1 字节载荷：

```
0x00 = 该块收下（块号推进）
0x0C = 拒收（数据窗口未开）
```

`0xA4` 数据族（屏保图像）：

```
[0]     0xA4                     magic
[1]     LEN（满块 0x40 = 64，收尾块 0x30 = 48）
[2..3]  块号 u16le（满块：低字节 + 高半字节；首块额外置 bit15）
[4]     0xC6                     —— 与上传侧的流控命令码同值
[5..]   数据（满块 58 字节，收尾块 42 字节）
末字节  CK = 前序字节和取低 8 位
```

上传序列共 2098 帧：`0xC4` 信息帧 → 2095 个满块（块号 2096 递减到 2）→ 1 个收尾块（块号 1）→ `0xC5` 提交。
首块的块号额外置 bit15，即 `0x8830`（`0x8830 ^ 0x8000 = 2096`）。
读图链路为 `0xC7` 起读（设备直接推第 1 帧）+ 反复 `0xC8` 取下一帧，直到计数器为 1。

### 3.6 一次交换的时序

协议帧里没有序号字段，所以"哪条应答属于哪次请求"由宿主侧配对解决。

- **总线串行器**（`blackSharkWire`）：按票号先进先出，一次只放一个交换进去。
  不用 `sync.Mutex` 是因为它不保证公平（进入饥饿模式前新来的会插队），而设备侧是一个任务缓冲、天然先来先服务。
- **等待槽**：`awaitCmd` + `awaitMission` 两个原子量声明"这次在等哪条命令"。
  读协程只把匹配 `awaitCmd` 的帧投进响应通道；设备主动上报（`0x06`、`0x07` 空应答等）不占通道。
- **声明必须早于发送**：设备可能回得比挂等待还快，若先发后挂，应答会被当"没人等"丢掉。
- **等待在锁外**：交换拆成"准备 + 发出"（持 `m.mutex`）与"等应答 + 收尾"（不持锁）两半。
  否则 1 Hz 推送、面板读、健康监控都会被排到一次交换之后；历史上锁内等待曾把多查询接口的持锁时间放大到约 20 s，
  触发健康监控误判系统睡眠并拆连接。锁序固定为 `m.mutex → m.link.wire`，收尾先放 wire 再回锁。
- **窗口**：例行查询 2 s；用户触发的写路径自读/回读 3 s；写发送 800 ms。窗口只在设备真的晚回时才用满。
  超时不重试 —— 设备出站排空速率固定，超时后立刻重发会让积压单调增长。
- **迟到应答暂存**：交换收尾会把 `awaitCmd` 清零，此后同 cmd 的应答若不接住，就与"设备根本没回"完全同形。
  按 `(cmd, 判别子)` 留一个短窗口队列（每键容量 8，条目自身 1.5 s 过期），下一次同 cmd 查询先取队列。
  判别子必须能从**应答自身**推出（`0x14` 用 `payload[0]` 低 4 位），推不出来的命令不进白名单 ——
  否则"槽 A 的答案"会被"问槽 B"的查询取走，静默返回错误数据，比超时更糟。
  写路径刻意不查暂存：旧 ACK 证明不了它响应的是哪一次写。
- **长任务同在一条队列里**：图传整轮占着总线串行器，期间其它交换排队等待（对齐官方"长包也是普通 mission"的形状）。
  唯一的例外是 1 Hz 的 `0x07` 推送：它拿到 busy 就不排队，改走不经串行器的直发（不挂等待、不排空），
  否则会被逐拍跳过，把设备唯一的周期性输入饿掉。

### 3.7 转速标定

标定表的唯一所有者为 `internal/deviceproto/blackshark_calibration.go`。
官方没有 sp↔RPM 换算（只有百分比到 sp 的映射），本表为自行实测所得。

注意 `sp` 与 `RPM` 是两种不同单位、数值也不同：出厂固定值 1200 对应实测 1410 RPM。

**固定形态 sp ↔ RPM**（`BlackSharkCalibration`，等稳态实测后做等张处理）

| sp | 800 | 1200 | 1600 | 2000 | 2400 | 2800 | 3200 | 3600 | 4000 | 4400 | 4800 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| RPM | 1410 | 1410 | 1440 | 2100 | 2310 | 2760 | 3210 | 3720 | 4020 | 4500 | 4740 |
| 标注 | 带0·地板 | 带0 | 带0 | 带0 | 带120 | 带0 | 带150 | 带0 | 带210 | 带150 | 带210·表顶 |

- 量程常量（唯一所有者）：`BlackSharkMinRPM = 1410`、`BlackSharkMaxRPM = 4000`、`BlackSharkRPMSnapRPM = 30`。
  上限对齐官方 app 曲线域的 100%（field 4000）；设备物理能力可到 4740 以上，但不再列为可选转速。
- 可选设定值区间相应封顶：`BlackSharkMinSetpoint = 800` 至 `BlackSharkMaxSetpoint = 4000`。
  标定表仍保留 4400 / 4800 两行，只用于设备回读 sp 的显示换算（探针或旧版可能把设备留在 >4000 的 sp 上）。
- 两条 RPM 路径均近似恒等，无孔洞与台阶（长保持实测，每点预热 4 分钟）：地板 1410，表顶 4740；
  设备上报的读数恒为 30 的整数倍。
- 标注中的"带 N"（0/120/150/210）理解为同一 sp 上的实测散布（推断）。若成立，则平台重复性约为 120~210 RPM。
- `sp` 与转速没有换算关系，把 sp 当作转速使用会越界。

**曲线形态 Field ↔ RPM**（`BlackSharkCurveCalibration`，曲线路径近似恒等）

| Field | 1440 | 2000 | 3600 | 3700 | 4000 | 4600 |
|---|---|---|---|---|---|---|
| RPM | 1410 | 1860 | 3600 | 3720 | 3990 | 4530 |

该表只用于界面换算（`ApproxActualRPM` 与可拖拽区间）；`BlackSharkCurveRangeForRPM` 返回
`1410..4000`（表末行覆盖 >4000 的回读区间，但可拖拽的上界夹在 `MaxRPM`）。
下发路径按 RPM 直接写字段，不经本表换算。

**手动挡位预设**（由 `BlackSharkManualGearPresets()` 从可选项量程派生）

派生方式：在 `[MinRPM, MaxRPM]`（1410~4000）上等分 12 个点并量化到 30 RPM，按每 3 点一档切成 4 档。
当前输出：

| 档 | 低 | 中 | 高 |
|---|---|---|---|
| 1 | 1410 | 1650 | 1890 |
| 2 | 2130 | 2340 | 2580 |
| 3 | 2820 | 3060 | 3300 |
| 4 | 3540 | 3750 | 3990 |

档内步进是量化结果（多为 240 RPM，末档低→中为 210），不是固定常量。最高一档落在 3990 而不是 4000：
4000 不在 30 RPM 的刻度上，量化后落到最近的可选刻度。预设值全部由后端派生，前端不硬编码。

**官方侧参照**：官方固定转速滑块为百分比（10~100），`sp = 1200 + (pct − 10) × 2800 / 90`，
1% 对应 31.1111，取整方式为向上取整（实测 5/5 吻合）。

- 官方速度域 `1200..4000` 与曲线点量程一致，且 1200 既是低噪档的固定 sp 也是低噪曲线首点，
  说明官方把 sp 与曲线点视为同一量。
- 官方滑块可以超过其超频预设 3534（实测拖出过 4000），说明 3534 只是预设值而非上限。

### 3.8 BLE 通道

BLE 档案（`builtin.blackshark.brb02.ble.rpm`）是与 USB 并列的一条通路，承载**同一套应用层帧**，
由 `internal/deviceprofileexec` 的 BLE 执行器负责收发。识别与特征见 §3.1。

| 能力 | BLE 支持 |
|---|---|
| 状态读取（`0x25`，并接收 `0x06` 通知） | 是 |
| 固定转速 / 曲线（`0x24`） | 是 |
| 灯效（`0x10`、`0x12`、`0x14`） | 是 |
| 屏幕图像上传 / 读回 | 是（预算按 BLE 取值，见 §4.3） |

与其他传输的差异：

- **校验规则与传输相关**：`0x07` 的回帧在 BLE 上走字节和，在 USB 上走 CRC16（见 §3.2）。
  解析器两条都试，并把"登记规则"与"命中规则"一起带出，不一致时按诊断信号处理。
- **没有 USB 那层 65 字节报文封套**：帧原样写到写特征上，一次写即可、不分片
  （协商后的单帧容量远大于最长的一帧，`0x24` 曲线 19 字节）。
- **两种写原语**：控制帧走 `WriteRaw`（跟随档案的 `BLEWriteWithResponse`），
  图传的块流走 `WriteRawStream`（强制不带响应写）—— 块流的流控由设备的 `0xC6` 逐块回答，
  每块再等一次 ATT 应答会污染整轮耗时基线。
- **写失败即判链路丢失**：执行器此时仍报 `IsConnected()`，健康监控不会自行发现，
  所以写路径失败要主动触发重连（异步，避免持锁）。
- **首块窗口更长**：BLE 上 `0xC4` 的应答与首块 `0xC6` 都可能迟至约 2 s，
  首块等待窗取 6 s，其余块仍为 2 s。
- **收帧入口同一个**：BLE 通知帧经钩子接进同一套收帧状态机，
  因此查询/等待逻辑不区分通路；钩子按执行器实例记录（断线重连会换对象，布尔量会让新实例永远接不上）。

## 4 出厂参数

数据来源为真机录制官方"重置"按钮期间的设备写入，录制脚本不操作任何控件，只记录流量。

`0x26` 读取的是设备当前存值（官方写完 `0x24` 后读回与写入值逐字节相同），不是出厂基准；
设备内也不存在独立的出厂副本。因此出厂参数的可靠来源只有下面两组"重置"常量。

### 4.1 散热

散热重置共 9 条 `0x24`，即 4 档各写固定形态与曲线形态，最后追加一条收尾。

```
tx 5.664  0x24  00 00 01 b0 04                                  # 档1 固定 sp = 1200
tx 5.775  0x24  00 01 01 14 b0 04 28 e8 05 3c 56 08 50 c4 0a    # 档1 曲线 1200/1512/2134/2756
tx 5.805  0x24  00 00 02 56 08                                  # 档2 固定 sp = 2134
tx 5.839  0x24  00 01 02 14 e8 05 28 56 08 3c c4 0a 50 32 0d    # 档2 曲线 1512/2134/2756/3378
tx 5.873  0x24  00 00 03 60 0b                                  # 档3 固定 sp = 2912
tx 5.907  0x24  00 01 03 14 1f 07 28 8d 09 3c 32 0d 50 a0 0f    # 档3 曲线 1823/2445/3378/4000
tx 5.935  0x24  00 00 04 ce 0d                                  # 档4 固定 sp = 3534
tx 5.969  0x24  00 01 04 14 56 08 28 fb 0b 3c a0 0f 50 a0 0f    # 档4 曲线 2134/3067/4000/4000
tx 5.999  0x24  00 00 02 56 08                                  # 收尾：当前切到「档2 + 固定」
```

| 档位 | 固定 sp（form=0） | 出厂曲线（form=1，20℃ / 40℃ / 60℃ / 80℃） |
|---|---|---|
| 1 低噪 | 1200 | 1200 / 1512 / 2134 / 2756 |
| 2 平衡 | 2134 | 1512 / 2134 / 2756 / 3378 |
| 3 强效 | 2912 | 1823 / 2445 / 3378 / 4000 |
| 4 超频 | 3534 | 2134 / 3067 / 4000 / 4000 |

- 重置后的生效状态为「档2 平衡 + 固定 sp 2134」：`0x25` 由 `00 01 01 14 b0 04 …` 变为 `00 00 02 56 08`，
  官方界面选中态也从 `radioButtonLowNoise` 转到 `radioButtonBalance`。
- 每条 `byte[0]` 为 `00`，即参照源为 CPU。
- 曲线温度点为 20 / 40 / 60 / 80 ℃，数值单位是 sp，不是 RPM。
- 设备当前存值不等于出厂值：用户调整过曲线后，`0x25` 读到的是调整后的结果。
- 常量存于 `deviceproto.BlackSharkOfficialCoolingResetBlocks`（9 条），
  `BlackSharkFactoryGearConfig` 从中取出某档位的出厂配置。

「恢复四档出厂曲线」走本项目自身的路径：先把四档方案曲线在**本机配置**里还原成出厂常量，
再把当前档位的曲线写进设备一次。写 `0x24` 的档位字段就是切档，所以不逐档写四遍 ——
逐槽写会把设备停在最后写入的槽，还容易撞上设备对控制查询的偶发沉默。
其余三档在下次切档时由既有下发逻辑覆盖。

主机侧调速模式下没有四档曲线（曲线集换成通用单方案），此时"重置"只把当前那条 17 点曲线还原成默认值，
设备侧一个字节都不写，见 §6.2。

### 4.2 灯效

灯效重置共 9 条 `0x12`，即 8 个槽位各写一次，再对槽位 1 写一次。

```
tx 2.333  0x12  01 be 0a 50 0a 00 00 00
tx 2.369  0x12  02 10 27 50 0a 00 00 00
tx 2.407  0x12  03 b8 0b 50 01 00 ff 49
tx 2.437  0x12  04 00 00 50 01 00 ff 49
tx 2.464  0x12  05 ee 02 50 01 00 ff 49
tx 2.492  0x12  06 8a 02 50 01 00 ff 49
tx 2.521  0x12  07 00 00 50 01 00 ff 49
tx 2.549  0x12  08 f4 01 50 0a 00 00 00
tx 2.579  0x12  01 be 0a 50 0a ff 00 00    # 第 9 条：槽位 1 再写一次，颜色设为红
```

字段对应：速度 = `payload[1..2]`，亮度 = `payload[3]`，单色/彩色 = `payload[4]`，颜色 = `payload[5..7]`。

| 槽位 | 灯效 | 速度 | 亮度 | 单色/彩色 | 颜色 |
|---|---|---|---|---|---|
| 1 | 彩色流动 | 2750 | 0x50（80） | 彩色 `0x0A` | `000000` |
| 2 | 彩色循环 | 10000 | 0x50 | 彩色 `0x0A` | `000000` |
| 3 | 呼吸 | 3000 | 0x50 | 单色 `0x01` | `00FF49` |
| 4 | 常亮 | 0 | 0x50 | 单色 `0x01` | `00FF49` |
| 5 | 闪烁 | 750 | 0x50 | 单色 `0x01` | `00FF49` |
| 6 | 响应 | 650 | 0x50 | 单色 `0x01` | `00FF49` |
| 7 | 音频同步 | 0 | 0x50 | 单色 `0x01` | `00FF49` |
| 8 | 刷新 | 500 | 0x50 | 彩色 `0x0A` | `000000` |
| — | 第 9 条（当前槽位 1） | 2750 | 0x50 | 彩色 `0x0A` | `FF0000`（红） |

- 重置后选中状态跳回「彩色流动」；未被选中的槽位同样会被重置，即 8 个槽位全部写一遍。
- `00FF49` 是出厂默认色，槽位 3、4、5、6、7 均使用该颜色。

**出厂默认表**（位于官方 exe `.rdata` `0x050ba9e4` 起，每条 24 字节，为字面量表而非计算结果）

| 模式 | 速度 | 亮度 | Field16 | ARGB | 类别 |
|---|---|---|---|---|---|
| 1 彩色流动 | 2750 | 0x50 | `0x0A` | `00000000` | 彩色 |
| 2 彩色循环 | 10000 | 0x50 | `0x0A` | `00000000` | 彩色 |
| 3 呼吸 | 3000 | 0x50 | `0x01` | `FF00FF49` | 单色 |

| 6 响应 | 650 | 0x50 | `0x01` | `FF00FF49` | 单色 |
| 7 音频同步 | 0 | 0x50 | `0x01` | `FF00FF49` | 单色 |

**图传的节拍与判据**

上传序列见 §3.5。三条与实现强相关的约束：

- **`0xC4` → 首个数据块之间必须留出足够时间**。设备的数据窗口在 `0xC4` 之后才开，窗口未开时
  灌进去的数据块会被**整轮**拒收（每块回 `0xC6` 状态 `0x0C`，块号不推进），设备保留旧图不变。
  真机逐档实测（整轮 2095 块）：首块落在 `0xC4` 后 0 ms / 530 ms → 全 `0x0C`；
  560 / 600 / 650 / 700 / 1000 / 1200 / 1500 / 3000 ms → 全 `0x00`。
  设备对 `0xC4` 的应答在约 0.5 s 后到达，**等到应答并不等于窗口已开** ——
  实测边界（530 ms 拒 / 560 ms 收）紧跟在应答之后，按应答时间发首块会擦着边界过。
  实现取 `blackSharkImageFirstBlockAfter = 1.2 s`（`0xC4` 起算的首块最小间隔）。
- **节拍由设备回执驱动，不用固定时钟**。每个数据块发完等一条 `0xC6`：`0x00` 继续，
  `0x0C` 退避 20 ms 后重发该块（上限 3 次）。等待窗常规 2 s；首块用 6 s，因为 BLE 上
  该应答与 `0xC4` 应答都可能迟至约 2 s，正好压住常规窗口。
  固定时钟只在 USB 上量过，照抄到 BLE 只会跑在设备前面并收 `0x0C`。
- **只有 `0xC6` 流控应答能判成败**。`0xC5` 回读是把设备手上那 11 字节信息载荷原样回显，
  整轮被拒时照样"与本机写入一致"，不能作为成功判据。发送方逐块计数，收下数为 0 而拒收数大于 0 时按失败上报。

**尾段**：最后一个数据块到提交帧（`0xC5`）之间留 165 ms 静默。官方实录在这里有
尾帧 → 心跳 → 提交的一串帧，本项目不发心跳，用等长静默替代，保证写入与提交之间有同样的间隔。

**图传是独占任务**

图传编排成一次带超时与取消的独占任务，而不是塞进"一帧一问一答"的例行查询：

| 位置 | 职责 |
|---|---|
| `CoreApp.beginBlackSharkImageTransfer` | 按 id 登记一次传输并挂 `context.WithTimeout`；登记表有互斥保护，已有传输在飞时直接报错 |
| `CoreApp.cancelAllBlackSharkImageTransfers` | 断开、挂起这类"设备要没了"的时刻取消全部在飞传输 |
| `Manager.SendBlackSharkImageWithProgress` | 真正的帧序列（复用 `deviceproto.BuildBlackSharkImageUpload`）并按帧上报进度 |
| `Manager.SetBlackSharkHostInfoRefreshInterval` / `blackSharkHostInfoRefreshLoop` | `0x07` 主机信息推送做成可设间隔的循环 |

时间预算由 `types.BlackSharkImageTransferBudget(transport)` 唯一给出：

| 通路 | 预算 | 依据 |
|---|---|---|
| USB | 90 s | 闭环节拍约 7 ms/块，整轮十几秒，留足余量 |
| BLE | 约 4.5 min | 2098 帧 × 100 ms + 60 s 余量 |

GUI 侧的 IPC 超时取自同一函数再加 1 分钟，保证"core 还在发帧、GUI 先判超时"的假失败不会出现。

编排层在传输前后暂停 / 恢复 `0x07` 推送，让 2098 帧的图传流是线上唯一的黑鲨流量；
独占窗口结束后强制重估自动控温目标并重播种温度 EMA（窗口里采样被饿住，直接沿用旧值会算错）。

**回读校验**：上传结束后读 3 次 `0xC5`（间隔 200 ms），比对大小与 CRC。
这是必要不充分的一致性校验 —— 一致不构成成功证据，它的价值在反向：
设备若没接收或没落盘，手上的元数据就不会是本次这张图。

**本机历史**：上传成功且回读通过后，把画布按 Unix 秒命名存到本机（保留最近 30 张，约 3.5 MB），
屏幕区可以点选其中一张重新上传。失败的半张图不入库。

### 4.4 开关

| 项 | 命令 | 取值 |
|---|---|---|
| 智能启停 + 通电自启 | `0x02`，2 字节向量 `[智能启停][通电自启]` | `0x01` 开 / `0x00` 关；`0x03` 可读回 |
| 灯效总开关 | `0x10` | `00` 关 / `01` 开 |
| LCD 屏开关 | `0xC0` | `00` 关 / `01` 开 |
| 温控参照 | `0x22` | `0` = CPU（`id0`），非 `0` = GPU（`id1`）；设备只有两态，越界值被钳到 1 |
| 散热模式 | `0x24` 的 `form` | `0` 固定转速 / `1` 智能变频；不可混用 |

冷却参照源不再单独读 `0x23`：`0x25` / `0x26` 的应答第 0 字节就是它（两条命令同形状），
调用方本来就要读其中一条，顺手取出即可，零额外查询。`0x23` 只在写 `0x22` 之后做一次回读校验。

官方持久化文件 `BlackSharkEquipmentBox.ini` 只保存 `coolingMode0..3`、固件版本与界面引导标记，
`ConfigDictionary.db` 为空（0 行），说明参照源一类的值不是 app 记录的用户偏好，而是随配置镜像下发。

## 5 维护注意事项

### 5.1 危险命令

`deviceproto.BlackSharkBlockedCommands` 是产品侧的唯一闸口，在 `blackSharkWriteGuard()` 中统一拦截，
名单只增不减：

| 命令 | 原因 |
|---|---|
| `0x04` `GetConfigSnapshot` | 实测发送后设备停止应答且不恢复（BLE 探针命令扫描，设备空闲、独占连接）；官方 app 也不发 |
| `0x05` `EnterBootMode` | 进入 BOOT 模式（固件升级用，本项目不刷写固件） |
| `0xF0` `RestoreFactorySettings` | 恢复出厂（不可逆） |
| `0xF1..0xF5` | 产线测试命令 |

该名单最初来源于一次盲目扫描命令码导致设备掉线 18 分钟；`0x04` 是后来在命令扫描中补进去的。
`0x27` 不在名单中，因为没有任何证据表明它危险。

### 5.2 与官方软件共存

- 启动官方 app 会静默终止 `Brb02Service.exe` 与 `BluetoothCommAgent.exe`。
- 官方软件约每 3 秒重写一次冷却配置，会覆盖外部写入。因此写入类实验必须先退出官方软件，否则结论不可用。
- 检查方式：`tasklist | findstr /i "BlackSharkEquipmentBox Brb02Service BluetoothCommAgent"` 应无输出。

### 5.3 实现约定

- **连接路径不做设备写操作**。`0x22` 在 `safeGo` 中延后 1.5 秒执行；候选循环持 `m.mutex`
  是 `Connect` 超时与设置页卡死的另一半原因。
- **`manager_wifi.go` 不是 WiFi 模块**。该文件声明的是 `//go:build !legacydevice` 下默认构建唯一的
  `type Manager struct`；Go 的字段只能写在结构体声明所在的文件，因此黑鲨的链路状态
  （`blackSharkLink`）与句柄都挂在这里。文件名属历史遗留，若要重命名需注意日志中的 caller 路径会随之变化，
  建议单独提交。
- **`legacydevice` 构建目标不可用，卡点不在黑鲨**。`device.go`（`//go:build legacydevice`）里是另一份
  不含黑鲨字段的旧 `Manager`；黑鲨代码在该标签下的报错来自第三方 `sstallion/go-hid`
  （其生成文件在缺少 cgo 的组合里引用不到 `BusType` 等常量）。
- **`Capabilities` 是门控而非标签**，界面卡片标签应使用 `DeviceProfile.DisplayFeatures`。
- **四类判据不合并**（§3.1）：句柄、BLE 发送器、链路就绪、写权限各自回答不同问题。
  黑鲨与飞智共用句柄字段，任何"是否黑鲨"的判断都必须带档案条件。
- **等待不持锁**：锁序固定为 `m.mutex → m.link.wire`；不要在持 wire 时去取 `m.mutex`
  （图传因此把句柄在入口快照，循环里不再进锁）。详见 §3.6。
- **接收通道不随断开清空**：读协程按 `connectionGen` 判代次，消费者每次使用前先排空，
  避免把陈旧帧当成新应答。
- **"没读到"不等于"设备是关的"**：开关类字段带 `Known` 标志，回读失败时不得覆盖已知值
  （合并规则见 `mergeBlackSharkSwitchStatesKnown`）。落盘缓存尤其要守这条，否则界面会显示成与实机相反的状态。
- **写 ACK 与读回是两条独立判据**：写 ACK 已到即证明设备受理，读回超时不算失败；
  读回拿到且与目标不符才是真失败。反过来，ACK 超时但读回确认生效时同样算成功。
- **`LearnedOffsets` 的长度由 `smartControlCurveLenFor` 统一决定**，
  遗漏任一调用点会导致长度翻转并静默丢失 80℃ 的已学偏移。切换变频实现方时，
  4 点与 17 点两套曲线的学习偏移要用 `smartcontrol.NormalizeConfigForUnit` 重新定长。
- **不要在第二处写同一个数值**：转速量程、标定表、灯效量程、图传预算都有唯一所有者（§6.1）。

### 6.2 变频与调速的写入约定

**两套实现，一个开关。** `cfg.BlackSharkHostVariableSpeed` 决定变频由谁实现，
判据只由 `blackSharkHostControlsSpeed()` 给出，分流点三处（调速入口、档位施加、监控循环的目标显示）——
判据一旦分叉，就会出现"主机以为在写下发、设备以为在看曲线"的半套状态。

| 项 | 设备侧跟随（开关关） | 主机侧调速（开关开） |
|---|---|---|
| 谁算转速 | 设备按曲线自己算 | 主机每拍算，按 `form=0` 固定值下发 |
| 设备里存什么 | 4 点真实曲线 | 一个固定设定值 |
| 曲线集 | 四档方案（每档 4 点） | 通用单方案（17 点） |
| 档位 | 有意义（1..4） | 无意义，设备档位固定写当前值 |
| 温度输入 | 主机推 `0x07`，设备按自己的曲线算转速 | 主机按曲线算好转速，设备只收结果 |

切换时两侧都要换桶：主机侧调速用通用单方案，设备侧跟随用四档方案。
不换桶会让曲线页继续显示 4 点（或 17 点），与当前实现方不符；换桶后立刻把学习偏移按新曲线定长。

**设备侧跟随的曲线下发**

- 要下发的 4 点由 `CoreApp.blackSharkDeviceCurvePoints` 组装：曲线来源取**该档的曲线方案**
  （不是 `cfg.FanCurve`，那只镜像当前生效的那一个方案）；先补两端点得到插值依据，再烘焙偏移 ——
  偏移数组是按依据的点序分配的，直接喂用户 4 点会让偏移整体错位。
- 取值与烘焙都走既有所有者：`smartcontrol.EffectiveCurveForUnit` + `temperature.CalculateTargetRPM`。
- 曲线字段按 RPM 直接写（曲线路径近似恒等，Field ≈ RPM）。
- 写入按 §3.5 的规则覆盖 CPU/GPU 两个参照源，回读当前配置（`0x25`）逐字段比对后才算生效。
- **每个"变频生效"的入口都必须显式补一次曲线写入**（`reassertBlackSharkInverterGear`：
  开启自动控制、温度遥测恢复 / 自动控制刚生效、连接后同步）。漏掉任一入口，设备会停在
  `form=0` 形态，而界面以为已经在变频。
- 保存某档方案时只在"该档正是设备当前档位"才写设备；编辑别的档位的方案不产生设备流量。

**主机侧调速的写入**

- 唯一入口 `setBlackSharkHIDTargetSpeedLocked`（两条通路共用，函数名里的 HID 只余历史含义）；
  它由上游的 `SetTargetSpeed` 在"黑鲨档案 + RPM 单位"时进入。
- **首次写入发完整 apply 仪式**：`0x24[FF 暂存] → 0x08 00 → 0x24[真实 src+值]`。
  依据是官方抓包里用户点保存时的那一次仪式：暂存帧的参照源字节是无效值（唤醒写入路径），
  闸门字节在两次 `0x24` 之间，真实帧最后写。
- **之后只发单帧提交**（`0x24[真实 src+值]`）。整个会话重放仪式是实测扰动源。
- **死区 100 RPM**：目标与上次实际写下的值相差不到 100 就不发帧。
  `0x24` 对设备是档位/形态级的重下发，上游 `MinRPMChange` 的节流挡不住温度噪声的逐拍小偏差；
  100 恰在设备判稳窗 `|实测−目标| < 101` 内，写与不写没有可观测差别。
- **最小写入间隔 5 s**：设备收到目标后按 200 ms/步渐变逼近，间隔内重发只会打断进行中的渐变。
- **写完不回读**：设备对控制查询偶发沉默数秒，回读会把已生效的写入误判成失败；
  生效与否由 `0x06` 状态帧的实测转速独立可观测。
- **状态失效**：`ResetBlackSharkSpeedWriteState` 清掉"上次发下的值"与仪式状态，
  让下一次写入重新走完整仪式。进入主机侧调速、还原快照、重置曲线这类"设备里生效的值不再是上次发的"
  场景都要调用它。

**共同的约定**

- **写 `0x24` 就是切档**（§3.5）：任何逐槽写之后都必须把设备拨回目标档位，而不只是恢复主机侧状态；
  固定与变频不可混，固定路径写 `form=0` 的该档固定值，变频路径写 `form=1` 的该档曲线。
- **插值端点为固定点**：左 `(10℃, MinRPM)`、右 `(100℃, MaxRPM)`，仅在曲线未覆盖时补齐
  （`BlackSharkEffectiveCurveForInterpolation`）；用户可拖动的 4 点温度取值域是 10~100 ℃，
  与端点同值但语义不同，不要合并。

**LCD 屏保联动**

主机侧调速接管期间，设备在固定转速形态下不跑屏保，所以开关一开就把 `0xC0` 写成关，
并按"接管前是不是开着的"记账（`cfg.BlackSharkLcdScreenBeforeHostSpeed`）。
两个方向的处理不对称，原因是固件：

- **开**：先读一次 `0xC1` 拿到原状态（读不到退回本机缓存；仍不知道就放弃，绝不记一个猜出来的值），
  记录**先落盘再关屏**，这样中途崩溃也不会丢掉"当初是开着的"。
- **关**：先把目标档位的曲线写回设备（设备侧跟随形态），等 300 ms，再恢复屏保。
  顺序反过来屏幕就回不来 —— 固件在固定转速形态下不接受"开屏"（`0xC0=1` 写入后 `0xC1` 读回仍是 0）。
- 恢复只按记录做，不读设备：读 `0xC1` 在 BLE 上常超时，一旦被读挡住，屏保会永久留在关闭态。
  恢复写失败会重试 3 次；仍失败则保留记录，由下次连接补做。

### 6.3 本机状态缓存与配置快照

**状态缓存**。开关族与四档配置只能从设备读到，每次进页面现读在 BLE 上代价很高
（多条查询、每条可到秒级）。因此后台回读一次、落盘一份：

- 字段：`cfg.BlackSharkStateCache`（`types.BlackSharkStateSnapshot`：开关族 + 四档配置）
  与 `BlackSharkStateCacheAtUnix`。其余字段是纯计算量或已有自己的缓存，重复缓存会造成双真值。
- 界面拿到的 `BlackSharkInfo` 带三个来源标记：`FromCache`（这份不是本次读到的）、
  `CachedAtUnix`（那份缓存的写入时刻）、`Refreshing`（后台正在回读校验）。
- 读取失败时**保留**缓存不动：把"读不到"当成"设备就是空状态"会让面板自己把自己清空。
  单条读失败（`Known=false`）也不覆盖已知值，见 §5.3。
- `BlackSharkInfo.Error` 与 `Available=false` 是两件事：前者表示"这次聚合没取到"（超时、设备不回），
  后者表示"不是黑鲨 / 没连上"。GUI 绑定不得在请求失败时返回零值结构体，否则界面会把读取超时
  谎报成"未连接黑鲨设备"。
- 曲线写入经设备回读确认后，顺手把那一档的曲线记进缓存（`rememberBlackSharkCurveVerified`），
  下次进页面不必再为它读一次。

**配置快照**（替代恢复出厂，可逆）。快照只包含能从设备读回的东西：

| 内容 | 说明 |
|---|---|
| 8 个灯效模式的参数 | 存 8 字节原始载荷而不是解释后的字段，还原时整块写回 |
| 当前生效的灯效模式 | `0x12` 写入即切模式，所以最后要把它选回去 |
| 四档曲线配置 | 只收 `form=1`（曲线形态）的档位；固定形态档位如实记为未纳入 |
| 开关族 | 灯效开关、LCD 开关、温控参照、智能启停、通电自启 |

不在快照范围内、且必须如实告知的两项：风扇开关（`0x20` 没有读回命令）、
屏幕显示参数（`0xC2` 只有写没有读）。任一字段读失败时快照里记的是兜底值，同时在
`Notes` 里列明，不要把它当作设备事实。还原按条目执行，逐项报告成功与失败，不做整体回滚。

### 6.4 协议变更时的处理

对官方二进制的机械枚举由维护方在仓库外执行，仓库内不保留生成产物。
枚举结果以本文 §3.4（主机侧构造点）与 §3.5（设备侧处理器集合、回帧频次）两张表为在库记录。

官方软件或固件升级后，重新枚举并对照本文 §3.4、§3.5，据此更新 `deviceproto.BlackSharkCommands`
的载荷长度、`AppParses` 与 `OfficialSignal` 列，同时同步更新本文对应表格，然后执行：

```
go test ./internal/deviceproto/
```

需要留意的两点：

- 枚举器只识别"在栈上直接摆帧"的构造形式。未出现在枚举结果中不等于官方不会发送该命令 ——
  载荷长度可变的命令由参数化路径构造，枚举不到。
- 载荷长度可变的命令若发生形态变化（例如增加一种新的载荷长度），
  `BlackSharkCommands[].PayloadLen` 为 `-1`，需要人工核对 §3.5 的载荷布局章节。
